# 研究の進み具合（2026-10-25）

家庭内 IoT 機器の通信をパッシブに監視する Quarant に、OSS（Zeek、Suricata）を組み込み、2 つの問いを公開データで調べた。数字の出どころは最後の「証拠の場所」にまとめた。

## 1. 問い

1. **見つける側**：消費者向け IoT の規格 ETSI EN 303 645 の要件のうち、通信を見るだけ（パッシブ）でどこまで判定できるか。
2. **減らす側**：見つけた問題に、家庭のゲートウェイでできる対策を組み合わせると、機器に手を加えずに脅威をどれだけ減らせるか。普通のルーターや一律の対策と比べて、何を足せるか。

SCIS 2027 に、この 2 つを 1 本にまとめて出すことを考えている。

## 2. 作ったもの

| 部分 | 中身 | 記録 |
|---|---|---|
| Quarant | 自前の分解（HTTP、TLS、MQTT、Telnet、FTP、RTSP）と、約 40 個のルール。すべての検出に、根拠の種類（観測／推定／照合）、観測した事実、推定、限界を付ける | [DESIGN.md](DESIGN.md) |
| Zeek の組み込み | Zeek が分解し（名前と形だけ、値は残さない）、Quarant が規格の要件の証拠に変換する。証明書、SSH、SNMP、ソフトウェアの版を追加 | D24、D27、D28 |
| 脆弱性の照合 | 通信に出る版を、NVD の影響を受ける版の範囲と手元で照合する。キャプチャより前に公開された CVE だけを数える | D28 |
| 重ね合わせ | Quarant と Zeek の結果を通信ごとに重ね、両方が出したものの確度を上げる | D25 |
| Suricata | 警告を機器ごとの証拠にする（規格の要件には対応づけず、対策の材料にする） | D26 |
| 対策の試算 | 証拠から対策のルールを作り、対策で止まる通信をキャプチャから除いて解析し直す | D29 |

## 3. 見つける側の結果

### 3.1 23 要件の到達度

規格の試験仕様（TS 103 701）を読み、通信を見るだけで判定に届く要件は 23 件と分類した（E3）。

| 状態 | 件数 | 要件 |
|---|---|---|
| 証拠として出せる | 7 | 5.1-2A、5.1-3、5.5-1、5.5-4、5.5-6、5.5-7、5.8-1 |
| 候補止まり | 12 | 5.1-1、5.1-2、5.1-5、5.2-2、5.3-4A、5.3-7、5.3-8、5.6-2、5.8-2、5.9-3、5.12-1、6-8 |
| 未実装 | 4 | 5.5-5、5.9-2、5.11-1、5.13-1B |

要件ごとの、パッシブで届く上限の見立てと次の作業：[assessment/passive-ceiling.md](assessment/passive-ceiling.md)。

### 3.2 OSS を組み込んで増えたもの

全データを同じ版で解析し、Quarant 単体と、Zeek の結果を重ねた版で、証拠が出た機器の数を比べた（[assessment/integration-rates.md](assessment/integration-rates.md)）。

| 要件 | UNSW 2016（24 台） | YourThings 2018（47 台） | UNSW-IoTraffic 2016-17（30 台） | 増えた理由 |
|---|---|---|---|---|
| 5.1-3、5.5-1 古い暗号 | 13 → 15 | 21 → 38 | 14 → 16 | 弱い証明書（RSA 1024、SHA-1）と SSH |
| 5.2-2、5.3-8 脆弱性のある版 | 0 → 2 | 0 → 6 | 0 → 2 | 版の照合（候補） |
| 5.6-2 版の開示 | 0 → 16 | 0 → 26 | 0 → 13 | Web サーバー、DHCP の版 |

CIC IoT 2022（2022 年の機器）では、版の開示（起動時 19 台、待機時 19 台）のほかは増えなかった。

### 3.3 精度

| 対象 | 確かめたこと | 結果 |
|---|---|---|
| Quarant 単体の検出 | 正しさ：検出の種類ごとに最大 15 件を抜き取って判定（E4） | 証拠に使う検出は正しかった（古い TLS 15/15、平文の Authorization 15/15 など） |
| | 網羅性：Zeek と生パケットの検索で別に正解を作って比べ、見逃しを直した（E11〜E14） | 一度も使っていない YourThings で、古い TLS 14/14、平文の秘密情報 8/8 |
| | 人による確認 | Claude の判定（要件の分類 78 件、見逃しの正解 41 件、対応づけ 23 件）を利用者が全件確認（R1）。基準の独立した判定の一致は 24/36（κ 0.19）なので、出現率は 2 通りの読み方で示す |
| OSS から足した検出 | まだ確かめていない | 抜き取りの確認と、要件への対応づけの利用者の確認が残っている |

## 4. 減らす側の結果

### 4.1 比べ方

同じキャプチャに、条件だけを変えて対策を当てた（[RESEARCH.md](RESEARCH.md) §9）。どの条件も普通のルーター（外から始まる接続を止める）の上に足す。家庭には普通のルーターが必ずあるので、Quarant なしの基準はルーターだけとした。

- 脅威の数：「機器 × 要件 × 攻撃者の位置」。規格の要件の証拠（確度 medium 以上）で数える。
- 止めすぎ：止めたパケットの割合。機能が壊れる危険の目安。
- 要件は、経路の危険（古い暗号、平文の秘密情報など。消えれば危険がなくなる）と、機器の性質（初期パスワード、脆弱性のある版など。届く範囲が狭まるだけ）に分けて読む。
- 学習してから守る形：前の期間の観測から対策を作り、後の期間に当てる。

### 4.4 分かったこと

1. 機器ごとの証拠から作る対策は、機器を知らない対策より多くの脅威を減らした。
2. ただ、学習から時間がたつほど効き目が落ちる（広いルールで、1〜3 か月後の 88〜100% から 4〜5 か月後の 67〜72%）。観測し直して計画を作り直せば、効き目は保てる。監視を続けながら対策を更新する使い方が要る。
3. 止めたパケットの大半は、映像の通り道に弱い暗号の証拠が出たカメラ 1 台だった（YourThings の Nest カメラ、UNSW の Nest DropCam）。危険な通り道が、機器の主な機能の通り道でもある。宛先やポートではなく、弱い接続だけを止める方法（TLS を読む侵入防止の仕組み）なら、この衝突を減らせるかもしれない。
4. 一律の対策では、平文のポートの一律遮断が、止めるパケットの少なさの割に効いた。許可リストは、時間がたつと宛先が変わり、止めすぎになった。

## 5. 限界と、これから固めること

| 点 | 内容 | どう固めるか |
|---|---|---|
| 物差しが Quarant 自身 | 脅威を Quarant の検出で数え、Quarant の対策も同じ検出から作っている | **確かめた（O10）**：Quarant にも Zeek にも頼らない生のパケットの検索で数え直しても、傾向は同じ（UNSW-IoTraffic で、広いルール 57〜100%、平文のポートの一律遮断 17〜43%）。4 か月後には、宛先ごとの対策（29%）が一律の遮断（43%）を下回った。[独立した物差しの表](assessment/countermeasure-iotraffic/raw-effect.md) |
| 止めすぎの数え方 | 1 台のカメラに引っ張られている | **確かめた（O10）**：機器ごとに数えると、Quarant は主な通信（パケットの半分以上）を 2〜9 台で止める。一律の対策は 0〜3 台 |
| 期間の数 | YourThings 1 回、UNSW-IoTraffic 5 回（独立した物差しでも 5 回） | 毎週ずらして 20 週ほど回す |
| データの古さ | 2016〜2018 年が中心 | Deakin IoT Traffic Dataset（2023〜2024 年、今の市販機器 24 台、CC BY 4.0）をダウンロード中 |
| 機器の振る舞い | 止められた機器の再試行や切り替えは、キャプチャの試算では分からない | 実機のテストベッドで確かめる（機材の案：[TESTBED.md](TESTBED.md)） |
| OSS から足した検出 | 正しさを確かめていない | 抜き取りの確認と、要件への対応づけの確認 |
| 機能 | 対策で機能が壊れるかは測っていない | 目的ではないが、考察で触れる |
