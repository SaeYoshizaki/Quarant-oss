# 設計判断の記録

新しい判断は末尾に追記する。覆すときは、元の項目を消さずに「Superseded by」を書く。

## D1 オフライン解析はキャプチャ時刻で動かす（2026-10-16）

- **判断**：時刻に関わる処理はすべてパケットの記録時刻で行う。対象は、イベントの時刻、フローの TTL、振る舞い検知の時間窓。
- **理由**：再現性と時系列比較が研究の前提だから。壁時計は、メタデータがないパケットの場合にだけ使う。

## D2 監視範囲を明示し、範囲外のホストを端末にしない（2026-10-16）

- **判断**：既定の監視範囲は RFC1918、リンクローカル、ULA とし、`--local-net` で変更できる。フローを持つ端末は、ローカル側の client を優先し、なければローカル側の server とする。
- **理由**：インターネット上のサーバーが端末一覧に入ると、新規端末通知を中心に誤検知が大量に出るから。

## D3 サーバー側の問題はサーバーに帰属させる（2026-10-16）

- **判断**：サービスの露出に関わる検出は、server がローカルなら server 側の端末に付ける。対象は I2 のサービス、HTTP 管理画面、LAN 内のサーバーへの平文リクエスト、Telnet。
- **理由**：リスクを持つのはサービスを公開している機器であり、接続したスマートフォンではないから。

## D4 根拠の種類を 3 値にする（2026-10-16）

- **判断**：`basis` は次の 3 値とする。
  - `observed`：検出のきっかけそのものが通信に現れていた。
  - `inferred`：ヒューリスティックや統計による判断。
  - `reference_match`：外部や知識 DB との照合。

  イベント型との対応は `analyzer/basis.go` で管理する。迷うものは `inferred` にする。
- **理由**：研究目的の「3 種類の情報を厳密に区別する」を、データ構造として保証するため。

## D5 CVE 候補は WARNING を上限とする（2026-10-16）

- **判断**：型番とファームウェアのバージョンが確認できない照合は `applicability=unconfirmed` とし、重大度は WARNING までにする。知識ベース側の重大度は evidence に残す。
- **理由**：「関連する CVE がある」と「脆弱である」は別のことだから（研究方針 5.8）。

## D6 振る舞い検知は説明可能な統計から始める（2026-10-16）

- **判断**：
  - スキャン：時間窓内の異なる宛先数と、未応答率で判定する。
  - 周期通信：間隔の中央値と、中央絶対偏差の比で判定する。
  - しきい値と測定値は evidence に書く。周期通信だけでは INFO とし、文脈フラグが 2 つ以上そろったら WARNING にする。
- **理由**：検証しやすく、誤検知の原因を追えるから。機械学習は Phase 3 以降に必要性を見て判断する。

## D7 脅威情報は一括取得してローカルで照合する（2026-10-16、Phase 2 で実装）

- **判断**：観測した IOC を 1 件ずつ外部に問い合わせない。
- **理由**：問い合わせそのものが利用者の通信を外部に漏らすから（データ取り扱い方針）。

## D8 知識ベースは go:embed で組み込む（2026-10-16）

- **判断**：`knowledge/*.json` と `knowledge/*.tsv` をバイナリに含める。`QUARANT_KNOWLEDGE_DIR` で差し替えられる。
- **理由**：カレントディレクトリに依存していたため、別の場所から実行すると失敗していたから。

## D9 正解ラベルつき合成シナリオで回帰を測る（2026-10-16）

- **判断**：`internal/synth` で生成した PCAP とラベルを、回帰テストと評価の基準にする。
- **注意**：検出器を知っている側が作ったデータなので、実環境での性能の根拠にはしない。実環境での評価には、実機または公開データセットが必要。

## D10 ルールは新しい情報があるパケットでだけ評価する（2026-10-17）

- **判断**：フローのバッファにも handshake の状態にも変化がないパケットでは、`rules.Run` を省く。
- **理由**：結果は変わらず、実 PCAP での処理時間が 53 秒から 7.6 秒になったから。

## D11 公開データセットで検証し、しきい値は開発用とホールドアウトに分ける（2026-10-17）

- **判断**：検出器のしきい値は、開発用データで決める（UNSW の 16-09-23、IoT-23 の 8-1）。誤検知は、調整に使っていないホールドアウト（UNSW の残り 19 日）で測る。
- **理由**：同じデータで調整と評価をすると、性能を過大評価してしまうから。

## D12 機器についての判断は機器単位で 1 回だけ出す（2026-10-17）

- **判断**：知識 DB との照合のように機器そのものについての判断は、機器と照合先の組み合わせごとに 1 回だけ出す。また、OUI と矛盾するファミリーとの照合は捨てる。
- **理由**：実データでは、1 台が 1 日に 1000 件以上の同じ照合結果を出していたから。また、接続先から推定したファミリーが、連携先のブランドを機器自身と取り違えていたから。

## D13 執拗な接続試行の検出器を追加する（2026-10-17）

- **判断**：`PERSISTENT_CONNECTION_ATTEMPTS`（1 時間に 30 回以上、同じ宛先へ接続を試みる）を追加する。WARNING にするのは文脈フラグが 2 つ以上ある場合だけ。
- **理由**：IoT-23 の Mirai と Hakai の C&C は、周期的ではない再接続ループだった（ばらつきの指標が 0.93）。周期通信の検出器では捉えられない。

## D14 TLS は内容で判定し、パーサは標準実装と同じ厳しさにする（2026-10-17）

- **判断**：
  - クライアントの最初のペイロードが TLS の ClientHello レコードであれば、ポートに関係なく TLS として解析する。
  - ClientHello は先頭からだけ解析する。報告する項目（SNI、対応グループ、ポイント形式、対応バージョン）を含む拡張は、構造が正確でなければ不正として扱う。
  - 解釈しない拡張の不正は許容する。
- **理由**：
  - 実データでは、ClientHello の 1.8〜3.7% が対象外のポートで送られていた。
  - 差分ファジングで、緩い解析が存在しない ClientHello を作り出したり、項目を読み落としたりすることが分かった（E2）。

## D15 判定基準は公式の評価仕様（ETSI TS 103 701）から導く（2026-10-17）

- **判断**：可観測性の分類基準は自分たちで作らない。TS 103 701 の試験ケースが何を必要としているか（IXIT、機器の操作、通信の観測、公開情報）だけから、機械的に導く（[assessment/RUBRIC.md](assessment/RUBRIC.md)）。
  - 判定の向き（合否とも／不合格のみ）を区別する。
  - 確かめられない仮定は、すべて書き出す。
  - 合否の基準が IXIT との比較であるものは、IXIT の中身を仮定で補わない（v2.1）。
- **理由**：恣意的な分類だという批判を避けるため。また、「不合格は示せても適合は示せない」という非対称性を、データとして扱うため。

## D16 観測者を 2 つのモデルに分け、独立した 2 回の分類と裁定で信頼性を確かめる（2026-10-17）

- **判断**：
  - 観測者を次の 2 つのモデルに分ける。主な結果はモデル N とする。
    - **N**：通信の観測と、第三者の参照情報（暗号カタログ、CVE、プロトコル仕様）
    - **ND**：N に加えて、製造者の公開文書
  - 分類は独立に 2 回行う。モデル N の食い違いは、文書化した原則（P-a〜P-e）で裁定する。
  - モデル ND は裁定せず、2 人の判断の幅として報告する。
- **理由**：
  - 1 つのモデルのままでは一致率が中程度（κ 0.44）にとどまり、食い違いの大半が「公開文書を IXIT の代わりにしてよいか」の解釈の違いだった。
  - 公開文書の審査は通信の観測ではないので、研究の問いのためにも分けるのが正しい。

## D17 応答を必要とする検出は、要求と応答の組で判断する。LAN 内の HTTP はポートではなく中身で判断する（2026-10-17）

- **判断**：
  - 「要求が受け入れられた」ことを条件にする検出は、サーバーのパケットで、最初の要求と応答の組を使う。
  - 既存の HTTP の検出は、これまでどおりクライアントのパケットで評価する。
  - LAN 内のサーバーへの通信は、ポート番号によらず、最初の要求行から HTTP と判断する。ただし、こうして判断した HTTP を使うのは、要求と応答の組を使う検出だけにする。既存の HTTP の検出は、これまでどおり既定のポートだけを対象にする。
- **理由**：
  - 認証なしのアクセス（5.5-4）や UPnP のポート開放（5.12-1）は、応答がなければ、拒否された要求と区別できない。
  - UNSW 2018 では、WeMo、Belkin NetCam、ゲートウェイの UPnP が、すべて既定の HTTP ポート以外で動いていた。
  - 既存の検出まで UPnP の通信に適用したところ、UNSW 2018 で次のようになった。どちらも、プロトコルが定める説明文書の取得（`GET /setup.xml`）を誤って検出したものだった。そのため、既存の検出には適用しない。
    - 初期設定用の画面が残っているという検出：約 5.9 万件
    - 平文の HTTP の検出：約 11 万件の増加
  - 合成シナリオでは、変更の前後でイベントが一致した。

## D18 パーサは標準実装と同じ構造の厳しさにし、TCP はシーケンス番号の順に組み立てる（2026-10-17）

- **判断**：
  - パーサは、標準実装と同じ構造の厳しさにする。
    - HTTP：ヘッダの終わりを 1 行ずつ探す。行の折り返しを前のヘッダにつなげる。
    - MQTT：固定ヘッダのフラグを検証する。MQTT 5 の will プロパティを読み飛ばす。
  - 意味上の規則の違反は許容する。対象は UTF-8 の検証、CONNECT のフラグの組み合わせ、ヘッダ名の後ろの空白など。
  - ペイロードを蓄積する方向ごとに、シーケンス番号の順にバイト列を組み立てる（`analyzer/reassembly.go`）。
    - 再送されたバイトは捨てる。順序が入れ替わった分は待ってから並べ直す。
    - 受信側の ACK が、キャプチャにないバイトを確認している場合は、キャプチャ側の欠落と判断する。その欠落を飛ばし、フローのレコードに `capture_gaps`／`capture_gap_bytes` として数える。
    - 証拠のない欠落は、最大 8 セグメントまで待つ。
    - 初期シーケンス番号は TCP のフラグ（SYN、SYN/ACK）から記録する。内容で TLS と判定する場合は、シーケンス番号がストリームの先頭に当たるセグメントで判定する。
  - UPnP の機器記述ファイルの取得、SOAP の制御、GENA のイベント通知は、管理画面、管理 API、設定用の窓口のヒューリスティクスから外す。
  - HTTP を内容で判定する範囲は、D17（ブランチ `detect-unauth-upnp` で記録。LAN 内、要求と応答の組を使う検出だけ）に従う。この判断では範囲を広げない。
- **理由**：
  - 差分検査（E2b）で、構造の緩さが存在しないヘッダや存在しないパケットを作り出すことが分かった。
  - 意味上の規則の違反があっても、そのバイト列がネットワークを流れた事実は変わらない。パッシブな観測者は、受け入れて読むのが正しい。
  - 届いた順に連結したバッファは、HTTP のストリームの 7〜23% で、本来のバイト列と食い違っていた。再送された要求のヘッダを本文として読む誤検知（1 日 35 件）の原因になっていた。
  - 外部のサーバーへの非標準ポートでの HTTP（例：8899 番ポートでの平文のログのアップロード）は、D17 の範囲では解析されない。この範囲を広げるかは、別途判断する（E2b）。

## D19 イベントは通信ごとに残し、機器 × 状態の要約を別に出す。フラッド系の検出器は今は作らない（2026-10-17）

- **判断**：
  - `events.jsonl` は通信ごとの記録として変えない。要約として `findings.json` を加える（`internal/findings`）。
    - finding：機器（MAC で同一視）× イベントの種類。件数、通信の数、宛先の数、最初と最後の時刻、根拠の種類、根拠の例（マスク済みの文字列を 160 字で切る）。
    - condition：機器 × 状態。同じ観測事実を、別の推定で言い換えているイベントの種類だけをまとめる（例：平文の HTTP を、API、クラウド、カテゴリの基準として読む 4 つのルール）。観測事実が違うもの（認証情報の露出ごと、古い TLS、証明書の異常）はまとめない。対応表は `conditionGroups` に置き、名前が実在するルールのものかをテストで確かめる。
    - 要約は新しい判断を作らない。深刻度と根拠の種類は、元のイベントのうち最も強いものをそのまま使う。根拠のない数値スコアも作らない。
  - フラッド系（TCP SYN、UDP、Ping、Smurf）の検出器は、今は作らない。
- **理由**：
  - S2 で比べると、正常データでの警告の総数は Suricata が 1 日 14〜18 件、Zeek が約 150 件だった。これに対し、Quarant は 1,579〜4,726 件だった。同じ状態を通信ごとに報告していたためで、件数のほとんどは重複だった。
  - 要約にしても、通信ごとの記録は監査（E4 の精度監査など）に必要なので残す。
  - フラッド系は、S2 でどのツールも検出できなかった。一方で、ETSI EN 303 645 の要件の可観測性という研究の中心とは直接つながらない。RQ の結果に必要になった時点で見直す。

## D20 既知の脆弱性の照合は、NVD で確かめた CVE がある製品ファミリーに限る（2026-10-17）

- **判断**：
  - I5 の知識ベースの各項目は、CVE ごとに、NVD の URL、対象製品、攻撃の経路、確認日を持つ（`references`）。
  - 確認済みの CVE が 1 件もない項目は、データとして残すが照合しない。外した CVE は、理由とともに `removed_references` に残す。
  - キーワードは単語やドメインのラベルの単位で照合する。ベンダー名のキーワードは、推定したベンダー名とファミリー名にだけ照合する。
  - 多くの機器が使う共有クラウドの名前は、接続先のキーワードに使わない。
- **理由**：
  - 記載されていた CVE 14 件のうち 5 件が、項目の製品に当てはまらなかった（[assessment/i5-references.md](assessment/i5-references.md)）。たとえば、ルーターの CVE がスマートプラグに、アプリの CVE が機器に対応づけられていた。
  - 出典のない「既知の脆弱性がある」という表示は、研究方針（断定しない、根拠を付ける）に反する。
  - 部分文字列での照合と共有クラウドの名前のせいで、無関係の機器が候補になっていた。

## D21 機器のカテゴリは、機器自身の名乗りから推定する（2026-10-17）

- **判断**：
  - カテゴリの根拠の順番を次のようにする。
    1. プロトコルが定める種類：HomeKit のアクセサリの種類（`ci=`）、標準の UPnP の機器の種類、mDNS の `_rtsp._tcp`。
    2. 機器が名乗る名前に含まれる一般的な語（DHCP のホスト名、mDNS の名前、DHCP のベンダークラス、ベンダーの UPnP の機器の種類）。
    3. 接続先のホスト名。1 と 2 で何も分からないときだけ使う。
  - スマートフォンと PC の目印（ホスト名、DHCP のベンダークラス、OS の名前）があれば、IoT のカテゴリを付けない。
  - ルーターとプリンターの目印（UPnP の機器の種類、印刷のサービス）は弱い手がかりとし、IoT のカテゴリの根拠がほかにないときだけ使う。
  - 製品名やベンダー名に合わせた規則は入れない。
  - 確信度は根拠の種類で決める：1 と 2 が一致すれば strong、1 だけなら high、2 だけなら medium、3 だけなら low。これまでは、3 だけでも常に strong だった。
  - 新しい名乗りが記録されたら、カテゴリを再計算する。
  - `I6_DEVICE_FLOW_CATEGORY_MISMATCH` は、機器が自分の種類を名乗っている場合は出さない。
- **理由**：
  - C1 で、接続先のホスト名から決めたカテゴリは 4 件に 3 件が誤りで、しかも確信度は strong だった。原因は 2 つ：ハブ、音声アシスタント、スマートフォンは連携先のクラウドにも接続すること、同じベンダーのクラウドが製品の種類をまたいで共通であること。
  - 機器自身の名乗りの方が、機器の種類を直接示す。プロトコルが定める語彙と一般的な語だけを使えば、特定のデータセットへの過学習を避けられる。
  - 評価用の 10 日で、付けたカテゴリの正解率は 38% → 77%、IoT ではない機器の誤分類は 10 → 0 になった（C1b）。

## D22 機器の名乗りは MAC アドレスごとにまとめ、解析をまたいで引き継げるようにする（2026-10-17）

- **判断**：
  - 機器のプロファイルは、これまでどおり IP アドレスごとに作る。そのうえで、名乗り（DHCP のホスト名とベンダークラスと要求パラメータ、mDNS、SSDP）を MAC アドレスごとの共有の記録に集め、同じ MAC アドレスのプロファイルがそれを参照する（`analyzer/device/linked.go`）。
  - ほかのアドレスから共有された名乗りは `via: same_mac`、前の解析から引き継いだ名乗りは `via: earlier_capture` を付けて `identity_evidence` に出す。カテゴリの根拠を、どこで観測した名乗りかまでたどれるようにするため。
  - `analyze` と `live` に `--identity-state` を加えた。ファイルがあれば解析の前に読み、解析のあとに保存する。保存するのは名乗りだけで、通信の内容は保存しない。ホスト名に人の名前が入ることがあるので、権限は所有者だけにする。時刻はキャプチャ時刻のまま残す。
  - 1 つの MAC アドレスの背後に複数の機器がいる場合（ブリッジ、MAC アドレスを変換する中継器）に備え、同じ MAC アドレスで IPv4 アドレスが行き来したら（A → B → A）、その MAC アドレスの共有をやめ、保存もしない。一方向の変化（A → B）は DHCP の再割り当てとみなして共有を続ける。
  - Belkin が自社の UPnP の名前空間で定める機器の種類（`controllee`、`lightswitch`、`insight`、`dimmer`、`bridge`）を、プロトコルの語彙として加えた。製品名ではない。
- **理由**：
  - C2 で、カテゴリを名乗る 6 台のうち半分が、名乗りを取りこぼして保留になっていた。mDNS の告知や DHCP の要求は、起動時や更新時にしか出ない。日ごとに独立して解析すると、名乗りが見えない日は保留になる。
  - 同じ機器が IPv4、IPv6 のリンクローカル、169.254.x のプロファイルに分かれ、名乗りもその間に分散していた。
  - イベントやルールは IP アドレスを単位にしているので、プロファイルの単位そのものを MAC アドレスに変えると影響が大きい。名乗りの共有だけなら、カテゴリの推定に必要な部分だけを変えられる。
  - 評価用の 10 日で、正解 34 → 55、保留 114 → 93、誤りは 10 のまま（C3）。
- **限界**：
  - 機器を譲渡したり、MAC アドレスを使い回したりすると、前の機器の名乗りが残る。`last_seen` で古さは分かるが、自動では消さない。
  - 引き継いだ名乗りは、今の機器の状態を示すとは限らない（例：ホスト名の変更）。

## D23 秘密情報とメディアの検出は、ポートやプロトコルを問わず中身で判断する（2026-10-17）

- **判断**（E11 の見逃しを受けて、利用者と相談して決めた。D17 の範囲を一部広げる）：
  - **HTTP**：中身で HTTP と判断した通信には、宛先（LAN 内、外部）とポートを問わず、秘密情報とメディアの検出だけを当てる（Authorization、URL のトークン、本文の秘密情報、Cookie、メディアのアップロード）。「初期設定画面が残っている」「平文の HTTP」など、それ以外の HTTP の検出は、これまでどおり既定のポートだけにする。
  - **UDP**：プロトコルを問わず、印字できる文字の `key=value` の並びに認証情報のキー（`user`、`pwd`、`password`、`token` など）があるものを検出する。値は記録しない。特定の P2P プロトコルの解析はしない。
  - **HTTP 以外の TCP**：暗号化されていない TCP の中に、JPEG（JFIF／Exif の見出しつき）や PNG の署名があれば、メディアの平文送信として検出する。数えるのは、機器から外部への送信だけ。
- **理由**：
  - E11 で、見逃しの原因のうち 3 件が「Quarant が読む範囲の外」にあった（LAN 内の 34100 番ポートの HTTP でのログイン、UDP の P2P 通信での外部からのログイン、独自プロトコルの中の JPEG）。どれも、すでに受け取っているパケットを読めば分かる。広げないと、パッシブな観測で見える証拠を「見えない」と数えてしまう。
  - D17 で誤検知が増えたのは、UPnP の説明文書の取得に、初期設定画面と平文の HTTP の検出を当てたためだった。秘密情報とメディアの検出は、プロトコルが定める文書の取得では反応しない。
  - E11 の正解では、どの拡張でも、IoT 機器での誤検知の候補はなかった（UDP の WSSE は要求ごとのダイジェストとして除外。残りはスマートフォンの STUN／WebRTC）。
- **限界**：
  - UDP と HTTP 以外の TCP は、パケットごとの検査で、複数のパケットにまたがるものは見つけない。
  - JFIF／Exif の見出しのない JPEG は見逃す（偶然の一致を避けるため、短い署名を使わない）。
  - LAN 内で機器がアプリに返す画像は数えない。5.8-1 の「関連するサービス」に LAN 内のアプリが入るかは、別に判断する。
- **追記（2026-10-18、E13）**：同じ考え方で、キープアライブの接続で続く要求（最大 16 件）も、秘密情報とメディアの検出だけにかける。あわせて、要求の本文は Content-Length で区切り、Content-Length も Transfer-Encoding もない要求の本文は 0 バイトとする（RFC 9112 6.3）。これまでは次の要求を本文として読んでいて、検出の理由を誤って記録していた。

## D24 Zeek を解析の土台として使えるようにする。Zeek は分解だけ、要件の証拠への変換は Quarant が行う（2026-10-19）

- **判断**（OSS の組み込みの手順 1、ブランチ `oss-integration`）：
  - `quarant zeek evidence --pcap` で、Zeek に専用のスクリプト（`internal/zeekevidence/evidence.zeek`）を付けて PCAP を読ませる。Zeek は HTTP、TLS、MQTT、FTP を中身で見つけて分解し、TLS の版と暗号、HTTP のヘッダーと URL の引数と本文のキーの名前、Authorization の方式、MQTT・FTP のパスワードの有無を出す。
  - 値は出さない。Zeek の標準のログ（URL、Cookie、FTP の引数をそのまま書く）は、すべての出力を止める。
  - Quarant 側（`internal/zeekevidence`）で、組み込みのルールと同じイベントの種類に変換し、根拠の種類、観測した事実、推定、限界、確度を付ける。`evidence-map.json` と集計のスクリプトが、どちらの結果にもそのまま使える。
  - イベントに `source` を加え、Zeek 経由のものは `source: zeek` とする。流れのキーは Quarant と同じ形にして、手順 2（重ね合わせ）で同じ通信を対応づけられるようにする。
  - 名前だけで判断したもの（ヘッダー、URL の引数、本文のキー）は確度を low にする。Zeek からは値の形が分からず、Quarant のように値の形で絞れないため。
  - 秘密の名前は、単語の境目にあるものだけにする（`password`、`x-auth-token`、`accesstoken`）。正解づくりの `gt.zeek` は名前のどこでも一致させていて、乱数の文字列の中の `pwd` を名前として拾っていた。
- **理由**：
  - プロトコルの分解を Zeek に任せれば、Quarant は規格の要件との対応づけと、根拠・限界の記述に集中できる。Zeek の分解は広く使われ、検証されている。
  - 種類をそろえれば、Quarant 単体と Zeek 経由を同じ物差しで比べられる（O1）。
- **限界**：
  - Zeek が分解しないもの（Telnet のログイン、UDP の `key=value`、HTTP 以外のメディア、RTSP）は、Zeek 経由では出ない。ファームウェアの更新、認証なしの操作、周期通信なども、まだ変換していない。
  - Zeek を組み込むと、Zeek を見逃しの正解（E11〜E14）に使えなくなる。

## D25 Quarant 自身の結果と Zeek 経由の結果を、通信ごとに重ねる（2026-10-19）

- **判断**（OSS の組み込みの手順 2）：
  - `quarant zeek merge --quarant DIR --zeek DIR --out DIR`（`internal/corroborate`）。同じ流れのキー・同じ種類の報告を時刻順に並べ、1 時間（`analyzer.FlowIdleTimeout`）報告がなければ区切る。Quarant は流れを 1 時間保ち、同じルールを 1 度しか出さないので、その区切りを 1 つの通信とみなす。
  - 両方が出したもの：Quarant のイベントを残し、`sources: ["quarant","zeek"]`、確度を 1 段上げる（low→medium→high）。限界に「一致したのは分解で、問題の重さではない」と書き足す。Zeek 側の重複は捨てる。
  - Quarant だけ：そのまま（`sources: ["quarant"]`）。
  - Zeek だけ：確度 medium 以上は証拠に加える（`sources: ["zeek"]`）。low（名前だけの一致、O1）は証拠にせず、`uncorroborated.jsonl` に分けて置く。
  - 出力の `events.jsonl` と `device_inventory.json`（Quarant のものを写す）は、集計のスクリプトでそのまま読める。
  - Zeek 経由のメディアの平文送信は確度を low にした（利用者と合意）。Zeek の内容判定は先頭のバイト列だけを見るので、短い本文を音声と取り違える（O1 の Philips Hue）。Quarant と一致したときだけ証拠になる。
- **理由**：O1 で、Zeek の名前だけの一致は判定済みのものがすべて秘密ではなかった。単独では証拠にせず、Quarant と一致したときだけ使う。TLS や認証情報は両方の分解が独立に一致するので、確かめの材料になる。
- **限界**：
  - 種類が違うと対応づけない（Quarant の `INSECURE_HTTP_AUTH` の `x-token` と、Zeek の `INSECURE_HTTP_TOKEN` など）。
  - イベントの時刻だけで区切るので、Quarant の流れの区切りとずれることがある（流れが続いている間に、最後の報告から 1 時間あとに来た報告を別の通信とみなす）。`flows.jsonl` があれば正確にできる。
  - 確度を上げても、値が秘密かどうかは分からないまま（Zeek は名前しか見ない）。

## D26 Suricata の警告を、機器ごとの証拠にする（2026-10-19）

- **判断**（OSS の組み込みの手順 3）：
  - `quarant suricata evidence --eve eve.json --out DIR`（`internal/suricataevidence`）。警告を、機器 × 種類 × ルール（sid）ごとに 1 件のイベントにまとめる（警告の数、flow の数、相手の数、最初と最後の時刻）。根拠の種類はすべて `reference_match`、`source: suricata`。
  - 種類（ルールの系統で分ける）：
    - マルウェア（ET MALWARE、TROJAN、CNC など）：`SURICATA_MALWARE_SIGNATURE`、medium。
    - 攻撃（ET SCAN、DOS、EXPLOIT、GPL SNMP など）で機器が送信元：`SURICATA_OUTBOUND_ATTACK_SIGNATURE`、medium。
    - 同じ系統で機器が宛先、かつ機器が応答した：`SURICATA_INBOUND_ATTACK_ANSWERED`、medium。応答は Suricata の flow の記録で判断する（TCP は SYN-ACK、ほかはパケットが返ったこと。RST だけは応答としない）。データを返したかも数える。
    - 応答のない攻撃：`SURICATA_INBOUND_ATTACK_SIGNATURE`、low。機器が狙われただけ。
    - 評判のリスト（ET DROP、CINS、COMPROMISED、TOR、JA3、危ない TLD）：`SURICATA_REPUTATION_MATCH`、low。リストはルールを取得した時点のもので、通信の時点のものではない（S2）。
    - 情報系（INFO、POLICY、CHAT、P2P など）と Suricata 自体の内部イベント：変換しない（件数だけ出す）。
  - 重ね合わせは `quarant merge --quarant DIR [--zeek DIR] [--suricata DIR] --out DIR` にまとめた（`zeek merge` も残す）。Suricata のイベントは流れのキーを持たないので Quarant とは対応づけず、low は保留に回す（D25 と同じ）。
- **理由**：Suricata は、Quarant にないシグネチャ照合（マルウェアの種類、反射攻撃）を持つ（S2）。対策（第 2 弾）では、乗っ取りの疑いや外から届くサービスが、隔離や遮断を選ぶ材料になる。
- **規格の要件との関係**（利用者と合意）：Suricata の証拠（外から届くサービス、乗っ取りの疑い）は、規格の要件には対応づけない（evidence-map に入れない）。第 2 弾の対策（遮断、隔離、宛先の制限）を選ぶ材料として、要件の証拠とは別に扱う。SNMP の初期の community を受け付けた例（O3）も、5.1-1 の証拠にはしない。
- **限界**：
  - ルールの系統で分けるので、系統の中の個々のルールの意味までは見ていない。
  - 応答の有無は flow の記録だけで見ていて、応答の中身（エラーかどうか）は分からない。

## D27 Zeek 経由に、証明書、SSH、SNMP を加える（2026-10-21）

- **判断**（OSS を広げる作業の 1 つめ。対象は YourThings 3/20 で実際に流れていたものから選んだ）：
  - **証明書**：TLS のサーバーの証明書（末端の 1 枚）で、鍵が短いもの（RSA・DSA が 2048 ビット未満、EC が 224 ビット未満）と、SHA-1・MD5 の署名を `I7_TLS_WEAK_CERTIFICATE_OBSERVED` とする。基準は NIST SP 800-131A Rev. 2。自己署名の証明書は、署名ではなく固定で信頼されるので、署名は見ない（鍵は見る）。
  - **SSH**：SSH-1（`I7_SSH_WEAK_VERSION_OBSERVED`）、RFC 9142 が SHOULD NOT・MUST NOT とする鍵交換、RC4（RFC 8758）と暗号なし（`I7_SSH_WEAK_ALGORITHM_SELECTED`）。CBC と `diffie-hellman-group14-sha1`（RFC 9142 では MAY）は数えない。
  - **SNMP**：v1・v2c のコミュニティ名を、Zeek のスクリプトの中で初期値（public、private）と照合し、一致したかだけを残す。値は残さない。エージェントが応答したときだけ証拠にする（`INSECURE_SNMP_DEFAULT_COMMUNITY`、`INSECURE_SNMP_COMMUNITY`）。応答のない要求（機器の探索、検査用のツール）は、どの機器についても何も示さない。
  - 要件への対応づけ（evidence-map.json）：証明書と SSH は 5.1-3、5.5-1、SNMP の初期値は 5.1-1、5.1-2、SNMP のコミュニティ名は 5.5-6、5.5-7。**対応づけは利用者の確認待ち**。
- **理由**：
  - 3/20 には、SSH が約 2,100 接続、SNMP が約 4,900 件、鍵が 1024 ビットか SHA-1 の署名の証明書が約 3,400 枚（中間・ルートを含む）あった。Quarant はどれも読んでいなかった。
  - Quarant の組み込みの証明書の検出は、期限切れ・自己署名・名前の不一致だけで、要件には対応づけていない。重ならない。
- **限界**：
  - TLS 1.3 は証明書を暗号化して送るので見えない。
  - 機器が証明書を検証したかは分からない。ハンドシェイクが終わらなかったものは確度を medium にする。
  - SSH は、実際に選ばれた方式だけを見る。サーバーがより強い方式も持っているかは分からない。
  - サーバー側の設定は、誰かが機器に接続したときだけ見える（YourThings では、データセットの作成者の検査用のツールの接続が多い）。

## D28 通信に出るソフトウェアの版を取り出し、公開された脆弱性と手元で照合する（2026-10-21）

- **判断**：
  - Zeek の software の仕組みで、家庭内の機器が名乗るソフトウェアの名前と版（数字の部分だけ）を取り出す。元の文字列と Zeek の「addl」は残さない（User-Agent に識別子が入ることがある）。
  - **版の開示（5.6-2）**：機器が誰にでも見せる場所に版を出していたら `I3_SOFTWARE_VERSION_DISCLOSED`。HTTP の Server ヘッダー、FTP の挨拶文、DHCP のベンダークラスは medium（どのプロトコルも版を求めていない）。SSH の版は、プロトコルが版の欄を求める（RFC 4253 4.2）ので low。UPnP の SERVER の文字列（UPnP の規格が OS と版を求める）は対象外。User-Agent は機器が自分のサービスに送るもので、開示に数えない。
  - **脆弱性のある版（5.2-2、5.3-8）**：名乗った版を、NVD の影響を受ける版の範囲と照合し、当てはまれば `I5_VULNERABLE_VERSION_CANDIDATE`（根拠は reference_match）。照合は手元の `knowledge/component_cves.json`（`scripts/knowledge/fetch_component_cves.py` で NVD API 2.0 と CISA KEV から作る。送るのは部品の名前だけ）。キャプチャより前に公開された CVE だけを数え、公開からの日数を残す。
  - 部品は、3/20 で機器が名乗っていたもののうち NVD に CPE があるもの：Dropbear、OpenSSH、lighttpd、BusyBox（udhcp の 1.x）、gSOAP、dhcpcd。
  - 確度：版の桁が範囲より少ないもの（gSOAP 2.7 と 2.7.x）と、多くのプログラムをまとめた製品（BusyBox）は low（単独では証拠にしない）。
  - 要件への対応づけ：5.2-2、5.3-8 を「未実装」から「候補」に、5.6-2 に版の開示を加えた。**対応づけは利用者の確認待ち**。
- **理由**：
  - 5.2-2、5.3-8 は、通信だけで手が届く要件のうち未実装だった。機器は版を通信に出していて、照合すれば候補になる。
  - 版の取り出しは Zeek に既にある。自分で作るより早く、広く使われている。
- **限界**：
  - 名乗った版が動いている版とは限らない。メーカーが版を変えずに修正を取り込むことがある。影響を受ける機能が組み込まれていないこともある。候補止まりで、確定には届かない。
  - 「長く放置した」の日数の基準は決めていない（根拠のない数値を作らない）。日数を記録するだけにする。
  - 照合できるのは知識ファイルにある部品だけ。uc-httpd、GoAhead など NVD の CPE がはっきりしないものは、まだ照合していない。

## D29 対策の効果は、対策で止まる通信をキャプチャから除いて解析し直し、残る証拠で測る（2026-10-21）

- **判断**（研究の第 2 弾の試作）：
  - `quarant countermeasure plan`：解析の結果（確度 medium 以上の証拠）から、家庭のゲートウェイで当てられる対策のルールを作る。対策は 3 つ。
    - **外からの接続の遮断**（block_inbound）：インターネット側から機器への接続を止める。
    - **弱い宛先の遮断**（block_weak_destinations）：平文の秘密情報やメディア、古い暗号が出た、インターネット側の宛先（アドレスとポート）への通信を止める。
    - **隔離**（isolate）：機器は、ゲートウェイとインターネットにだけ通じ、家庭内のほかの機器とは通じない。マルチキャストとブロードキャストは止めない（同じネットワークの中には届く）。
  - `quarant countermeasure filter`：ルールで止まる通信のパケットをすべて除いたキャプチャを書く。それを同じ手順で解析し、`scripts/assessment/countermeasure_effect.py` で、要件ごとに証拠が残る機器を数える。
  - 既存の `quarant mitigate`（OpenWrt のルールの案）は使わない。根拠が文書化されていない重み（既知の問題 2）が絡むため。
- **理由**：
  - TCP の接続をゲートウェイが始まりで止めれば、機器は中身を送らない。止めた接続のパケットを除くことは、ゲートウェイの外の観測者・攻撃者から見えなくなるものに当たる。
  - 機器にも実際のネットワークにも手を加えずに、公開データで対策の効果を測れる。
- **読み方**：要件を 2 種類に分ける。
  - **経路の危険**（5.1-2A、5.1-3、5.5-1、5.5-6、5.5-7、5.8-1）：証拠が消えれば、その危険がなくなる。
  - **機器の性質**（5.1-1、5.1-2、5.2-2、5.3-8、5.6-2）：対策の後も機器の中身は変わらない。減るのは、誰がそれを見られるか、届くか。証拠が消えても「危険がなくなった」とは書かない。
- **限界**：
  - 対策の後に機器がやり方を変える振る舞い（再試行、別の宛先、別のプロトコルへの切り替え）は再現できない。
  - 対策で機能が壊れるか（アプリから LAN 内で操作できなくなるなど）は測らない（目的ではない）。
  - UDP は最初のパケットから中身を運ぶので、止めても最初のパケットは LAN 内に出る。
